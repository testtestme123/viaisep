【Karpathy 编码准则】（必须遵守）

1. 三思而后写（Think Before Coding）
   - 在输出 JSON 之前，在注释中简要说明你的实现思路
   - 如果某个需求有多种合理的实现方式，列出权衡，不要暗中选择
   - 不隐藏困惑——如果你需要更多信息才能做出好的决策，在你的 json 输出中附加一个 // TODO: 注释
   - 暴露任何你正在做的假设

2. 简约至上（Simplicity First）
   - 如果某段逻辑能用更少的代码表达，就必须简化
   - 不添加未要求的特性、抽象、灵活性或错误处理
   - 不需要为单次使用的场景创建辅助函数或基类
   - 不处理在当前逻辑下不可能发生的异常场景
   - 删除本变更造成但未使用的导入、变量和函数

3. 外科手术式变更（Surgical Changes）
   - 只生成目标集合中列出的文件，只动必须动的那部分代码
   - 不改进相邻代码，不重构未损坏的东西
   - 匹配现有代码的风格，而不是强迫代码适应你的偏好
   - 只清理你自己变更造成的混乱，不清理预先存在的死代码
   - 每行变更都应直接追溯到用户的请求

4. 目标驱动执行（Goal-Driven Execution）
   - 在生成代码之前，先用注释列出验证标准
   - 如果任务是模糊的（如"添加验证"），将其转化为可验证的目标
   - 例如："为无效输入编写测试，然后让测试通过"
   - 每一步完成时在生成的代码中附加 verify: [检查项] 注释

【输出格式】
必须返回一个包含 `files` 和 `discovered` 两个字段的 JSON 对象：

{
  "files": {
    "{{src_file_example}}": "文件内容...",
    "{{test_file_example}}": "文件内容..."
  },
  "discovered": {
    "nodes": [],
    "edges": [],
    "rules": [],
    "ontology_classes": []
  }
}

- `files`：键为相对文件路径，值为文件完整内容
- `discovered`：AI 在生成代码过程中发现的额外信息（新节点/边/规则/本体类）
- 如果没有发现新信息，`discovered` 中的数组设为空数组
- 不要返回 Markdown 代码块或解释文字，只返回纯 JSON

discovered 各字段说明：
- nodes: [{"type": "Module|Capability|...", "name": "名称", "description": "描述"}]
- edges: [{"source_id": "节点ID", "target_id": "节点ID", "type": "depends_on"}]
- rules: [{"name": "规则名", "conditions": [...], "action": "动作", "description": "..."}]
- ontology_classes: [{"name": "类名", "data_properties": [], "extends": "Module/.../null"}]

发现规则：
1. 代码使用了图谱未体现的模块间依赖 → 作为 edge 写入
2. 代码实现了图上未建模的业务规则 → 作为 rule 写入
3. 发现需求中未建模的业务概念 → 作为 ontology class 写入
4. 新增 node 需要 name 和 type，系统自动分配 ID；source_id/target_id 可用节点名称（系统自动解析）
5. 只写**新发现**的结构，不写用户已手工创建的内容

【安全约束】（必须遵守）

1. 硬编码密钥禁止
   - 禁止将 API 密钥、密码、Token、secret 等敏感信息的字面量写入代码
   - 必须通过环境变量或配置文件加载
   - 示例：{{security_env_var_correct}}
   - 反例：{{security_env_var_wrong}}

2. 危险函数禁止
   - {{security_danger_func_note}}
   - 外部命令调用必须使用参数数组形式，禁止拼接 shell 命令字符串

3. SQL 注入预防
   - 所有数据库查询必须使用参数化查询（占位符）
   - 禁止使用字符串拼接构造 SQL 语句
   - 正确：{{security_sql_correct}}
   - 反例：{{security_sql_wrong}}

4. 路径遍历预防
   - 禁止使用 open() 访问 ../ 和绝对路径
   - 文件路径访问必须限制在当前项目目录内
   - 用户提供的文件名必须进行清洗（移除 ../、~ 等）

5. 安全默认值
   - 所有 API 端点必须有输入校验（类型、范围、格式）
   - 会话 Token 必须使用 httpOnly + secure + sameSite cookie
   - 错误消息不暴露堆栈跟踪和内部实现细节
   - 日志不记录密码、Token、完整信用卡号等敏感数据

6. 安全检查
   - 每个外部输入接口（API 路由、表单处理）必须在边界校验
   - 每个认证端点必须有速率限制
   - 所有动态执行必须验证输入来源可信

【代码质量准则】（必须遵守）

1. 命名规范
   - 变量名必须具有业务含义，禁止使用 temp、data、result 等无上下文的名字
   - 函数名使用动词开头（get_、validate_、process_等），类名使用名词
   - 布尔变量/函数使用 is_、has_、should_ 前缀

2. 控制流简洁
   - 避免超过 3 层嵌套，超过时应提取为独立函数
   - 禁止使用嵌套三元表达式
   - 循环内避免深层的 if/else，使用提前返回（guard clause）

3. 函数长度控制
   - 单个函数不超过 50 行（含空行和注释）
   - 超过 30 行时应考虑拆分为子函数

4. 死代码预防
   - 删除未使用的导入、变量和函数
   - 不要留下无用的 catch/except 块
   - 不要留下 TODO 或 FIXME 标记在生产代码中

5. 边界条件处理
   - 所有公共函数参数必须进行 None/空值检查
   - 列表访问前检查索引范围，字典访问使用 .get() 而非 []
   - 所有文件操作和网络调用必须有错误处理

6. 架构一致性
   - 遵循现有模块的导入模式，不引入新的反模式
   - 不创建循环依赖（A 导入 B，B 不能导入 A）
   - 抽象层次匹配：utils 层不调用业务层函数

7. 性能基础
   - 避免在循环中重复计算不变表达式
   - 数据库查询添加 LIMIT 限制
   - 列表推导优于显式 for 循环构建列表

【UI 设计 Token 规范】（当生成的项目包含前端 UI 时遵守）

1. 设计 Token 定义
   - 生成 UI 代码时，必须创建 `design_tokens.json` 文件，包含三类全局 Token
   - color：主色（primary）、辅助色（secondary）、背景色（background）、
     文字色（text）、边框色（border）
   - typography：正文字号（body.size）、标题字号（heading.size）、字体族（font.family）
   - spacing：基础间距（base）、内边距（padding）、边框圆角（border.radius）

2. Token 使用规范
   - 在 CSS 中通过 `var(--{category}-{key})` 引用设计 Token
   - 在 JS 中通过常量引用设计 Token，禁止硬编码与 Token 值不一致的样式值
   - `design_tokens.json` 格式：
     ```json
     {
       "color": {
         "primary": "#2563eb", "secondary": "#64748b", "background": "#ffffff",
         "text": "#1f2937", "border": "#e5e7eb"
       },
       "typography": {
         "body.size": "14px", "heading.size": "20px",
         "font.family": "system-ui, sans-serif"
       },
       "spacing": { "base": "8px", "padding": "16px", "border.radius": "6px" }
     }
     ```

3. UI 质量标准（来自 frontend-ui-engineering）
   - 组件架构：偏好组合而非过度配置，分离数据获取与展示
   - 可访问性：所有交互元素必须可通过键盘操作，使用语义化 HTML 和 ARIA 标签
   - 全覆盖：空状态、错误状态、加载状态都必须处理，禁止只渲染"理想状态"
   - 响应式设计：至少覆盖 320px（移动端）、768px（平板）、1024px（桌面）三个断点
   - 避免 AI 审美：不使用紫色渐变、超大圆角、统一卡片网格等 AI 生成常见模式
